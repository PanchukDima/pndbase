# Архитектура проекта

Проект постепенно переводится из плоского Qt Widgets-монолита в слоистую структуру.
Перемещение всех экранов одним большим коммитом намеренно не выполняется: пути `.ui`,
сгенерированные классы и многочисленные прямые include делают такую операцию слишком
рискованной без UI-тестов.

## Целевая структура

```text
src/
  app/                  точка входа и composition root
  core/                 контекст приложения и общие политики
    application/
  domain/               предметные типы без зависимости от UI и SQL
    user/
  infrastructure/       PostgreSQL, файлы, сеть, журналирование
  ui/                    окна и диалоги по функциональным областям
    auth/
    settings/
models/                  Qt-модели, переходно остаются отдельно
work_info_patient/       legacy-модули карточки пациента, мигрируют по одному
journal/                 legacy-журналы, мигрируют по одному
database/                схема, bootstrap и синтетические данные
docs/                    архитектура и результаты review
```

## Уже выделенные объекты

- `domain::UserSession` хранит идентичность, права, участки и отделение пользователя.
- `core::ApplicationPaths` хранит разрешенные приложением пути.
- `ApplicationContext` является единым владельцем этих объектов.

`Objects_app` временно оставлен как alias, а старые имена полей как ссылки на новые
объекты. Это позволяет мигрировать около сотни legacy-обращений постепенно, не
ломая приложение одним массовым изменением. Новый код должен использовать:

```cpp
auto &context = ApplicationContext::instance();
if (context.userSession().hasRight(29)) {
    // ...
}
```

## Правила последующего рефакторинга

1. UI не формирует SQL. Запросы переходят в repository/service классы.
2. Все пользовательские значения передаются через `QSqlQuery::prepare/bindValue`.
3. `QObject`, созданный через `new`, получает parent либо явного RAII-владельца.
4. Предметные идентификаторы хранятся числовыми типами, а не `QString`.
5. Один функциональный модуль содержит `ui`, service, repository и модели рядом.
6. Новые зависимости передаются конструктором. Статические переходные aliases не расширяются.
7. После каждого переноса выполняется чистая Linux/Qt6-сборка.

## Следующие безопасные этапы

1. Выделить `DatabaseSettings` и `DatabaseConnectionFactory` из экранов login/settings.
2. Выделить `PatientRepository` и `PatientService`, начиная с read-only загрузки карты.
3. Разделить `MainWindow` на coordinators вкладок пациента.
4. Разделить `Dialog_patient` на редактор демографии, учета, документов и комментариев.
5. Перенести legacy-каталоги в `src/ui` по одному функциональному модулю.
6. Добавить Qt Test для входа, поиска пациента и CRUD тестовой карты.
